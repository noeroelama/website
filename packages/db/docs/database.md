# Database

## Decision: MySQL for everything except sign-in (2026-10-31, DEC-19)

All data — content, events, registrations, organization/chapters, members, newsletter,
audit log, API keys and the shop — lives in **MySQL 8 on the cPanel host**: ONE database shared
by every environment. Firebase is used **only for Authentication** (one user pool, session
cookies). Uploaded files are on the cPanel disk (`files.md`).

Browsers never talk to the database: every read/write goes through our servers.

## How it is stored

`packages/db/src/sql/store.ts` is a small **document store on MySQL**: every collection below is a
table `(id VARCHAR(255) PRIMARY KEY, data JSON, dates JSON)`, created on first use from
`src/sql/collections.ts` (a new collection is one line there). Its API is the document API the
repositories already used (get/set/create/update/delete, `where` / `orderBy` / `startAfter` /
`limit` / `count`, `getAll`, `runTransaction`, `batch`), so the move off Firestore changed no
repository logic. Details:

- Queries filter with `JSON_EXTRACT` (paths and values are always bound parameters); `orderBy`
  leaves out rows without the field and orders by `id` last; ranges never match `null`.
- Dates are stored as ISO strings (they sort and compare correctly) and their paths are kept in
  `dates`, so reads give timestamps with `toDate()` back.
- Transactions: every read locks its rows (`SELECT … FOR UPDATE`), reads come before writes, the
  writes are applied together and committed; deadlocks and lock timeouts are retried (5 tries,
  then `code 10`, like Firestore's `ABORTED`). `create` of an existing id fails with `code 6`.
- Tables hold a few thousand rows each, so JSON filters without extra indexes are fine.
  Shortcut: when a table grows past ~100k rows, add a generated column + index for its hot
  query (e.g. `auditLogs.occurredAt`).
- The contract is tested against a real MySQL 8 in CI (`tests/integration/sql-store.test.ts`,
  `TEST_DATABASE_URL`); repository logic is tested with the in-memory `tests/support/fake-db.ts`.

## Rules

- **Ports in `domain`**: each module declares the repositories it needs. Domain code never sees the database.
- **Adapters in `db`**: `mysql2` is imported only in `packages/db/src/sql/store.ts` (lint-enforced).
- **Per-role access**: `@website/db` exposes repositories per `DatabaseRole`
  (`web_ro`, `admin_rw`, `shop_rw`, `gateway_rw`); each app connects with its own MySQL user
  (`DATABASE_URL`), so it can be revoked on its own.
- **No UI database access**: apps reach `@website/db` only from `src/server/**`.
- **Every editable document** has `version` (optimistic concurrency), `createdAt`, `updatedAt`,
  `deletedAt` (soft delete). Writes are transactions conditional on `version`.
- **Expiring rows** (`rateLimits`, `webauthnChallenges`, `webhookEvents`) carry `expiresAt` and are
  deleted by the admin cron job `expire` (`apps/admin/docs/cron.md`).

## Documents with a URL slug

`src/sql/slugged.ts` (`createSluggedStore`) is shared by content, events, gallery albums and chapters: one
transaction reads the document (version check, trash refused), lets the caller build the new
fields, keeps the slug unique through the `*Slugs` index collection, and writes the document and
its audit entry. Soft delete sets `deletedAt`; the slug stays reserved so a revert can restore it.

## Known trade-offs

| Area                   | Risk                                       | Mitigation                                                                                         |
| ---------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Shop orders/inventory  | Rules live in code, not in SQL constraints | Transactions for order + inventory + counters; payment provider is source of truth                 |
| Popular event capacity | Hot counter row                            | Row lock on `eventCounters` in the registration transaction                                        |
| Reporting/exports      | JSON documents, no joins between tables    | `JSON_TABLE` / `JSON_EXTRACT` in phpMyAdmin for one-off reports; purpose-built queries in code     |
| Search                 | No full-text search                        | Prefix fields for small lists; MySQL full-text on a generated column only when needed              |
| Audit immutability     | The MySQL user can technically update rows | No update/delete code path; hash chain; nightly dumps kept off the server (`disaster-recovery.md`) |

## Performance rules

- **Connection pooling**: `getDatabaseForRole()` creates one pool per database URL per server
  process (`DATABASE_CONNECTION_LIMIT`, default 5) and reuses it for every request. Never open a
  connection per request. Passenger may run several processes per app: keep the sum under the
  plan's MySQL connection limit.
- **No N+1 queries**: to load documents for a list (e.g. the profiles of an event's registrants),
  collect the ids and call `getDocumentsByIds(db, collection, ids)` — one query per 100 ids,
  duplicates fetched once. Never call `doc(id).get()` inside a loop.
- **Race conditions**: read-modify-write goes through `runTransaction` (row locks); editable
  documents also carry `version` for optimistic concurrency (stale writes fail with
  `ConcurrencyConflictError`, shown to staff as "conflict").
